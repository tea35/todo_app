### 学んだこと・気づき

**アーキテクチャ分離の効果**
- Repositoryパターンにより「何を保存するか」と「どう保存するか」が分離された
- 将来SharedPreferences→sqfliteやFirebaseに変更する際、Repository内部だけ書き換えれば済む設計になった

**Riverpodの基本概念**
- `Provider`: 値やインスタンスをアプリ全体で共有するための入れ物
- `Notifier`: 状態(state)とそれを操作するメソッドをまとめたクラス。`build()`が初期状態を返す
- `state = ...`と代入するだけで、それを監視しているWidgetが自動的に再描画される(setStateの明示呼び出しが不要に)

**watch と read の使い分け**
- `build()`メソッド内で表示用データを取得する → `ref.watch()`(変化を監視し、再描画をトリガー)
- ボタンのonPressedなどコールバック内でメソッドを呼ぶだけ → `ref.read()`(一度だけ取得、監視しない)
- ここを間違えると「値が変わっても画面が更新されない」「不要な再描画が起きる」バグにつながる

**イミュータブルな状態更新**
- Riverpodは新旧のstateを「参照(オブジェクトの同一性)」で比較して変化を検知する
- そのため既存リストの中身を直接書き換えるのではなく、常に新しいリスト/オブジェクトを作ってstateに代入する必要がある
  (例: `state = [...state, newTodo]`)
- Reactの`useState`でのイミュータブル更新(`setTodos([...todos, newTodo])`)と全く同じ発想で理解しやすかった

**設計の全体像**
lib/
  models/         ← データの形
  repositories/   ← 保存・読み込みロジック
  providers/      ← 状態管理ロジック
  screens/        ← UI表示のみ
という層分けにより、責務が明確になった(Next.jsのAPI層/状態管理層/コンポーネント層の分離と同じ発想)
